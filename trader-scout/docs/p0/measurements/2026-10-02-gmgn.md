# 2026-10-02 — GMGN OpenAPI probe (Tier 2 aggregated market data)

## Setup

Installed `gmgn-cli` (v1.6.6) via `npm install -g gmgn-cli` under a user-local npm prefix
(`~/.npm-global`, `prefix` reconfigured to avoid `EACCES` on the system Node install — no
sudo/system-wide install performed). Configured via `gmgn-cli config` (generates an Ed25519
keypair locally, embeds the public key in a GMGN key-creation URL) then
`gmgn-cli config --apply <key>`, storing the key in `~/.config/gmgn/.env`
(`chmod 600`, outside this repo's tree — no `.gitignore` entry needed). `gmgn-cli config --check`
returned exit 0.

**Key handling note**: the key value is never reproduced in this file, in commit messages, or
anywhere else in the repo — only the config path (`~/.config/gmgn/.env`) and the CLI invocation
shape are referenced. Per this session's standing practice with the Helius/Blockscout keys: the
key transited the chat in plaintext (the user pasted it directly), the same exposure class as
those keys. Rotation was previously declined by the user for Helius/Blockscout; the same applies
here — noted once, not re-raised per probe.

## Capability enumeration (via `--help`, not inferred from marketing copy)

`gmgn-cli --help` exposes: `token` (info/security/pool/holders/traders), `market`, `portfolio`
(holdings/activity/stats/profits/info/token-balance/created-tokens), `track` (follow-wallet/kol/
smartmoney trade records), `swap`, `multi-swap`, `order`, `gas-price`, `cooking`. The capability
actually probed here is `token traders` (`GET /v1/market/token_top_traders`).

`gmgn-cli token traders --help` documents: `--chain`, `--address`, `--limit` (default 20, max
100), `--order-by` (`amount_percentage` / `profit` / `unrealized_profit` / `buy_volume_cur` /
`sell_volume_cur`), `--direction`, `--tag` (wallet classification filter:
`smart_degen`/`renowned`/`fresh_wallet`/`dev`/`sniper`/`rat_trader`/`bundler`/`transfer_in`/
`dex_bot`/`bluechip_owner`), `--raw`.

## Rate limit — confirmed empirically, not just from docs

First probe returned `HTTP 429 code=429 error=RATE_LIMIT_BANNED` with an explicit reset timer
("~21s remaining"), matching the free-tier leaky-bucket documented elsewhere (5/5 rate/capacity
at weight 1 for token routes). A second probe after waiting past the reset window succeeded.
**Lesson for any future batch use of this capability: one request at a time, respect the
`RATE_LIMIT_BANNED` reset window exactly — repeated requests during a ban extend it (documented
in the error message itself: "up to 5 minutes").**

### Cross-check against our own decoded data — honest result: zero overlap

Our `6EF8rr...` bonding-curve `buy` decoder, run against the single transaction in our committed
5-tx probe that touches this mint (tx[2]), found exactly **one** buyer:
`HgwBZM6kQE8qpYBdM2aXDxaEs5GTpDryNxuREeVP8f8B` (account position `[6]`, `user`, per the confirmed
IDL layout — see `docs/p0/deployment-registry.md`'s 2026-10-01 confirmation section).

**This address does not appear in GMGN's top-20 by `profit` for this mint.** This is not a bug in
either system — it is explained by scope mismatch, not a discrepancy to "fix":

- Our sample is **one transaction** from a 5-transaction probe window (`slot 452380124`,
  `txIndex 645`) — a single buy, no visibility into whether that buyer ever sold, or what their
  realized profit was.
- GMGN's `last_block` values for its top 3 (`452379880`, `452380796`, `452380795`) span a wider
  range than our single captured slot, meaning GMGN is aggregating the **mint's full trade
  history**, not just our narrow window.
- GMGN's top traders by `profit` have `sell_tx_count_cur` of 5-19 — multi-cycle traders. Our one
  buyer's single buy, with no sell activity captured in our sample, would not surface near the top
  of a profit-ranked list regardless of whether they eventually profited, since we have no sell
  leg to compute profit from at all.

**Conclusion: a meaningful overlap experiment (P0.7) requires either (a) a GMGN pull across the
mint's full lifetime compared against our own decoder run across the same full lifetime, or
(b) picking wallets GMGN ranks highly and checking whether *our* decoder, run against *their*
full trade history for that wallet, reproduces compatible economics.** A single-transaction
sample on each side cannot establish overlap or divergence — this probe closes the "can we talk
to GMGN at all, and does its data look sane" question, not the overlap experiment itself.

## What this does NOT establish

- Completeness of GMGN's trader list for a mint (is "top 20 by profit" the full set of distinct
  traders, or a subset of a larger universe?) — not determined here.
- Whether GMGN's `profit`/`realized_pnl` figures are internally consistent with on-chain SOL/token
  balance deltas at the per-transaction level (would require decoding GMGN's `native_transfer` and
  `token_transfer*` sub-objects against our own `getTransactionsForAddress` data for the same
  signatures — not attempted here, out of scope for a first connectivity probe).
- Rate-limit behavior under sustained/concurrent use (only the single-request ban-and-recovery
  cycle was observed).

## Tier classification (per `docs/p0/source-capability-matrix.md`'s own taxonomy)

GMGN is **Tier 2 — aggregated market data** per invariant #16: pre-computed trades/PnL by a third
party, never a ledger source of truth. Legitimate uses here: discovery-candidate generation
(wallet addresses to feed into our own `buyer-intersect`/`wallet-rank`) and cross-checking our own
computed numbers — a divergence is a signal to investigate our own decoder, not evidence GMGN is
right. Any GMGN-sourced PnL figure that enters `scout-ledger` must go through
`acquire_unverified`/`ExternalDataOptIn` (ADR-008 S5), never the strict verified path.
