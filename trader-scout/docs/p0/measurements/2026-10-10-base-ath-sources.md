# Источники ATH для Base — 2026-10-10

Цель после уточнения: заполнить ATH для всех eligible Base-токенов, сохраняя отсутствие данных как unknown. Исследование сочетает официальную документацию и ограниченные read-only запросы к Codex. Полный обход не запускался; таблицы БД не изменялись.

## Текущее состояние

В проекте реализован только Codex-адаптер: он передает известные адреса пачками до 200 и читает `token.extrema.athFdv` и timestamp ([`ath.rs`](../../../crates/scout-devtracker/src/ath.rs)); eligible кандидатов отдает БД ([`ath_candidates`](../../../crates/scout-devdb/src/lib.rs)). Переданные для исследования текущие Base-оценки: около 10,3 млн токенов в БД, 9,5 млн eligible, из которых 8,8 млн пока без наблюдения ATH. Прямой запрос пачки из 200 известных ID теоретически означал бы около 44 тыс. запросов, включая запросы для токенов, которые Codex не индексирует.

На текущем периоде Codex dashboard показывает 5,5 тыс. из 10 тыс. бесплатных запросов израсходованными; остаток около 4,5 тыс. запросов. Официальная [страница тарифов Codex](https://www.codex.io/pricing) указывает 10 тыс. запросов/месяц за $0 после одноразовой активации $1; план Growth начинается с $350/месяц за 1 млн запросов, переплата — $350 за миллион. Покупка тарифа здесь не предполагается.

## Проверка Codex-фильтра

Официальная схема [`TokenFilters`](https://docs.codex.io/api-reference/input-objects/tokenfilters) содержит `network`, `athFdv` и `athCircMc`; Base имеет network ID `8453`. Документация [`filterTokens`](https://docs.codex.io/api-reference/queries/filtertokens) подтверждает до 200 результатов на запрос, offset-пагинацию, возможность передать до 200 известных ID и то, что неиндексированные ID просто отсутствуют в ответе. Там же сказано, что токен попадает в поиск после swap. Это индекс провайдера, а не полный реестр всех токенов или доказательство полноты ATH.

Проведены четыре read-only GraphQL-запроса к `https://graph.codex.io/graphql`, без вывода или сохранения authorization headers. Ответы сохранены в [probe JSON](../../../.scout-data/diagnostics/codex-base-positive-ath-pagination-probe.json).

| Проверка | Результат |
|---|---|
| `network:[8453]`, `isTestnet:false`, `includeScams:true`, `athFdv:{gt:0}`, `createdAt ASC`, `limit:200`, `offset:0`; выборка включает пару `createdAt`, адрес, networkId, extrema, holders, liquidity | HTTP 200, 43,559 байт, 0,827 с; 200 результатов, у всех extrema и положительный `athFdv`. Документированный `count` оказался количеством на странице (200), не общим размером выборки. |

| `limit:1`, `offset:10000` | HTTP 200 с GraphQL-ошибкой `Limit + Offset cannot be greater than 10000`; значит API не позволяет пройти дальше 10 тыс. записей одним поиском. |
| `athFdv DESC`, `limit:200`, `offset:200` | GraphQL validation error: `athFdv` не является допустимым `TokenRankingAttribute`. |

### Разбиение по закрытым дням

Документация `TokenFilters` задает `createdAt` как unix-время создания первой пары. Проверен фильтр `createdAt:{gte:start,lt:end}` для закрытых UTC-дней с теми же параметрами сети, scams, `athFdv > 0` и `createdAt ASC`. Четыре запроса сохранены без auth headers в [дневной probe JSON](../../../.scout-data/diagnostics/codex-base-ath-day-probe.json).

| День UTC | Offset 0 | Offset 200 | ATH |
|---|---:|---:|---|
| 2026-10-09 | 200 результатов, 0,952 с | 200, 0,406 с | Все 400 имеют `extrema` и положительный `athFdv`; границы `createdAt` возрастают без пересечения страниц. |
| 2026-10-08 | 200 результатов, 0,453 с | 200, 0,627 с | Все 400 имеют `extrema` и положительный `athFdv`. |

Значит, date partition устранил timeout на проверенных первых страницах и позволяет продвигать offset в пределах маленьких дневных выборок. Это не доказывает, что обработаны все результаты этих дней: обе страницы были полными. День с более чем 10 тыс. подходящих записей все равно упрется в API offset cap и потребует деления диапазона `createdAt` на более короткие интервалы. Данные не подтверждают наличие положительной ATH у всех токенов: фильтр `athFdv > 0` намеренно исключает токены с null/zero ATH.

Отдельный диагностический `limit:1` без фильтра ATH вернул самый старый найденный токен с `extrema:null`; прямые Codex-запросы по небольшой выборке старых `codex-missing` ID не вернули их даже при `includeScams:true`. Значит, unindexed/без-extrema случаи существуют; отсутствие результата нельзя записывать как нулевой ATH или считать токен ниже порога.

Вывод теста: фильтр `athFdv > 0` позволяет найти положительные ATH, которые сам Codex индексирует, а разбиение по UTC-дням делает offset-пагинацию быстрой на измеренных Base launch-днях. Это хороший путь перечислить провайдер-известных кандидатов дешевле, чем 44 тыс. отдельных запросов известных ID. Но два первых 400-токенных пакета в двух днях не устанавливают полный объем, daily interval cardinality, completeness всех исторических периодов или ATH для токенов без данных. Полнота для отсутствующих в Codex mint-адресов недостижима этим поиском.

## Следующий безопасный шаг

Не запускать прямой перебор 8,8 млн адресов через Codex: расчет 44 тыс. пачек превышает оставшийся месячный лимит примерно в 10 раз, а многие неизвестные провайдеру адреса дадут пустой ответ. Для bulk-перечисления использовать только закрытые UTC интервалы `createdAt` с `athFdv > 0`, поддерживать cursor по дню/подинтервалу/offset и делить интервалы при приближении к 10 тыс. offset. До запуска измерить количество запросов на полной нужной истории и закрепить жесткий budget ниже остатка 4,5 тыс. Недостающие/null/unindexed токены из DB-сопоставления должны остаться unknown/coverage-gap, а не исчезнуть из учета.

Для настоящего полного заполнения всех eligible токенов, включая токены без наблюдаемой рыночной цены/ATH, просмотренные документы не подтверждают бесплатный или низкозатратный API. Понадобится измеренная альтернативная стратегия, например выборка нескольких подтвержденных пулов и on-chain реконструкция из сделок, с явным диапазоном блоков и coverage metadata. Любой пропуск истории должен оставаться unknown; это исследование не меняет определение ATH или поведение ledger/DB.

## Открытые проверки

- Почему unsliced all-history запрос `offset:200`, `createdAt ASC` timed out; дневные интервалы работают, но полное перечисление еще не замерено.
- Сколько Base-результатов реально попадает под `athFdv > 0` по всей истории и каков требуемый бюджет запросов.
- Частота дневных интервалов, требующих subdivision, из-за offset cap 10 тыс.
- Как перечислять ATH-null, unindexed и непрайсованные токены без потери их unknown-статуса.
- Покрытие пулов и цена полного OHLCV восстановления на репрезентативной выборке Base.
- Фактическое Base/history покрытие Birdeye.
