# Birdeye ATH discrepancy: lifecycle and pool validation — 2026-10-11

## Finding

The saved 1D Birdeye token charts do **not** establish full launch-to-present pool coverage for any of the five comparison tokens. Some series start on the local launch date, but the Birdeye candle artifacts contain no launch transaction, canonical pool/curve address, migration transaction, or pool-by-pool candle history. Token-level `/defi/v3/ohlcv` and exact-pair `/defi/v3/ohlcv/pair` answer different questions: Birdeye explicitly describes pair candles as one venue's behavior, rather than token-level aggregation. A daily `high` should capture an intraday wick represented in that candle; the unresolved risks here are omitted dates, index start, market selection, and lifecycle continuity—not a generic need for sub-day candles.

## Primary-source lifecycle facts relevant to validation

- **Birdeye:** [token OHLCV V3](https://data.birdeye.so/docs/data-api/price-ohlcv/get-defi-v3-ohlcv) is token-address scoped. The documented pair route is `GET https://public-api.birdeye.so/defi/v3/ohlcv/pair`, requires `X-API-KEY`, `x-chain`, a **pair contract address**, timeframe and Unix-second bounds, and returns up to 5,000 candles. Birdeye says pair-scoped candles represent one venue; empty candles are omitted unless padding is enabled. Its docs list `base`, `bsc`, `solana`, and `robinhood` as supported `x-chain` values. See [pair OHLCV reference](https://data.birdeye.so/docs/data-api/price-ohlcv/get-defi-v3-ohlcv-pair). This is the exact documented endpoint for checking a known curve/pool; it does not discover all relevant pools or prove retention/completeness.
- **Pump.fun:** its [bonding-curve docs](https://pump.fun/docs/bonding-curve) say every coin starts on a reserve-priced curve and graduation atomically, irreversibly migrates liquidity to PumpSwap, which becomes the canonical pool. A proper coverage test therefore needs the specific curve-phase history plus the destination PumpSwap pool, joined at the migration boundary. The docs do not establish that Birdeye's token series includes both.
- **Four.meme:** first-party token pages such as [this migrated example](https://four.meme/token/0xcaae2a2f939f51d97cdfa9a86e79e3f085b799f3) state that bonding-curve liquidity is deposited into PancakeSwap at graduation and show pool migration status. For the sampled BSC address, verify its own Four.meme create/graduate events and resulting PancakeSwap pair; the generic lifecycle cannot identify its address-specific status.
- **Flap:** [bonding-curve docs](https://docs.flap.sh/flap/developers/basic-and-mechanism/bonding-curve) say tokens trade against a curve before DEX graduation; `getTokenV5` is the recommended per-token source for immutable curve parameters because parameters vary by deployment/quote asset. [Migration docs](https://docs.flap.sh/flap/developers/basic-and-mechanism/list-on-dex) describe migrating remaining supply and reserves to a DEX, with V2/V3 destination variation. Its [event-indexing guide](https://docs.flap.sh/flap/developers/wallet-and-terminal-and-bot-developers/index-token-created-events) specifies reading `TokenCreated`, curve/threshold, `TokenMigratorSet`, and `TokenDexPreferenceSet`; together the last two resolve protocol shape and DEX. That page maps Robinhood `DEX0` to Uniswap and `DEX1` to PancakeSwap, unlike BNB Chain's mapping. However, Flap's published [deployed-address directory](https://docs.flap.sh/flap/developers/deployed-contract-addresses) lists BNB mainnet and other networks but no Robinhood deployment. The local index's RH `flap` label is not proof of a first-party Flap deployment or the sampled token's lifecycle; treat that relationship as unverified.
- **Pons on Robinhood (4663):** current [Pons docs](https://docs.ponsfamily.com/) describe V1 direct Uniswap V3 pool at launch, no curve and no later migration. Separate [Pons V2 docs](https://docs.ponsfamily.com/v2) describe a bonding curve followed by graduation into a Uniswap V4 pool. The integration docs expose factory launch events/pool addresses and state that V1 graduation continues in the same pool ([events and contract reads](https://docs.ponsfamily.com/)). Thus launch date and “Pons” label alone are insufficient: determine the exact factory/version and use its emitted pool address(es). Do not infer every Pons token’s lifecycle from its label. Existing user-approved migration gates remain unchanged; any future decoder-semantics correction requires separate evidence and ADR.

### Address-specific Pons version check

The saved [lifecycle DB rows](../../../.scout-data/diagnostics/birdeye-lifecycle-db-rows-2026-10-11.json) resolve `0xfa89…a603` as `source=robinhood:pons:launch`, tx `0x2957dd5e…31c6c54f1`, block `54,358,195` (`2026-09-04T15:05:17Z`), and `source=robinhood:pons:migration`, tx `0xfee34ca9…0c4066f8`, block `54,465,757` (`2026-09-04T18:06:38Z`). In [`evm_ingest.rs`](../../../crates/scout-devtracker/src/evm_ingest.rs), those source keys each filter the sole `PONS_FACTORY = 0x7eD598BcEf8bd9Edd8C97A195C6d13f40801EC7e` emitter; the launch topic0 is `0x8d4aad4953d0ca700d468f3753aa14432d1b35b43ec6409f051fb6aa43a89607` (`TokenLaunched(address,address,address,address,uint256,uint256)`), and the migration topic0 is `0x0a44ef75df69c534f43cd6c1aa3ef8983065fe5fe79ef9e79f6494e6f258c259` (`PoolGraduated(address,uint256,uint256,uint256)`). The official [Pons V2 contract docs](https://docs.ponsfamily.com/v2) identify that exact address as the Pons factory on Robinhood Chain (4663), and describe `TokenLaunched` as recording each new launch/curve and `PoolGraduated` as “Pool created and the position locked.” The [pinned-source registry](fixtures/README.md) identifies this as `PonsV2LaunchFactory` and contrasts V1's `PonsLaunchFactory` at `0xA5aAb3F0c6EeadF30Ef1D3Eb997108E976351feB`. This ties the sampled token's fact rows to **Pons V2**, whose graduation is a curve-to-new-Uniswap-v4-pool transition—not a Pons V1 graduation marker. The migration row's `pool=null` is a current decoder omission: `pons_migration` extracts only token from the event and stores no pool ID/address. The saved [all-time facts audit](../../../.scout-data/diagnostics/year-facts-audit-2026-10-11.json) records all configured Robinhood event-source cursors at block 0; this launch and graduation are inside that scanned range (blocks `54,358,195`–`54,465,757`). It still does not identify the destination pool or establish Birdeye coverage.

Pons V1 is distinct: its official [integration docs](https://docs.ponsfamily.com/) say launch creates a Uniswap V3 pool immediately, graduation continues in the same pool, and “There is no migration event.” The dev-tracker `EVM_SOURCES` entries are configured only for the V2 factory above, so the current `robinhood:pons:migration` facts do not count V1 graduation status as migration. This resolves version ambiguity for the sampled token; it does not establish discovery of every historical Pons deployment or full lifecycle candle coverage.

## Bounded validation proposal

Use only the five existing addresses and the already-supplied Birdeye key; no new token discovery or broad scan is needed.

1. Use the parent-saved exact launch/migration rows in `.scout-data/diagnostics/birdeye-lifecycle-db-rows-2026-10-11.json` for launchpad, block/time, transaction, migration block/time, and source. They confirm the Pons V2 emitter for `0xfa89…a603`, but leave its per-token curve and V4 pool identifier unknown; resolve the curve from `TokenLaunched` and the pool key/ID from Pons V2 launch/graduation records. Pons V2's post-graduation venue is a Uniswap V4 pool keyed in a shared PoolManager, not necessarily a standalone pair contract; Birdeye's pair OHLCV endpoint requires a pair contract address, so support for a Pons V4 pool ID is unverified. Do not pass a pool ID as a pair address without provider documentation.
2. For each address, use the launchpad’s own event/contract record to resolve the actual curve and each canonical pool, including destination DEX and pool address. For `0xfa89…a603`, use the already-matched Pons V2 factory/source; for other Pons tokens, branch on their actual factory/version. For RH Flap, first prove the launch used a valid deployed contract on chain 4663 rather than infer it from a label.
3. Query the documented Birdeye **pair** OHLCV V3 route for each resolved DEX pool address, using `type=1D`, `currency=usd`, `mode=range`, `padding=false`, and a bounded window from pool creation through the last date in the token chart. A launchpad bonding curve is not automatically a Birdeye “pair”; verify that the endpoint recognizes the curve address before treating it as a source, otherwise the curve phase needs a launchpad/on-chain trade-history source. Compare each indexed pool's `max(high)` and exact day labels to the token-level series and Codex `athPrice`; do not silently combine markets. Record an absent pool response/date as unknown until the endpoint semantics explain it.
4. For any proposed FDV comparison, require supply at the candle/ATH time (or explicitly label price × current supply as a current-supply diagnostic). Do not rewrite Codex ATH/FDV fields from this check.

This small test can answer whether these five discrepancies line up with lifecycle or pool selection. It cannot establish provider-wide retention, every-pool aggregation for arbitrary tokens, or coverage of all launches. Keep existing user-approved migration/eligibility gates unchanged; this is a data-provenance diagnostic, not a policy change.
