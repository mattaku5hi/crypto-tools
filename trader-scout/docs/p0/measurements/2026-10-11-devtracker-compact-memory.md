# Dev-tracker compact PostgreSQL memory benchmark — 2026-10-11

A fresh restore of the immutable 2.837 GB runner snapshot completed successfully in an isolated PostgreSQL 16.15 container configured with a 1 GiB memory cap, no swap, one CPU, 512 MiB shared memory, `shared_buffers=128MB`, `work_mem=4MB`, `max_parallel_workers_per_gather=0`, and `max_connections=32`. `pg_restore` used `--single-transaction --exit-on-error --no-owner --no-privileges`; it exited 0. Container start to restore completion took about 5m06s; the exact restore start was not recorded.

The restored database contained schema migrations 1–8, 1,354,410 ATH rows, 193,967 migrations, 941 cursors, and 1,525 developer histories. Database size after restore was 17,106,000,919 bytes. The release binary (`15dbbe0a…`) ran `derive --since-days 365` against the clone and exited 0 in 3m05.90s. It processed 27,464,274 launch rows and 4,324,447 creators, yielding 718 category members. The output had 12 Base, 94 BSC, 28 Robinhood, and 584 Solana members. Category labels overlap: top-runners 71, top-migr 498, and win-streak 161. The command emitted JSONL only; it did not export or send lists.

The derive process peaked at 52,552 KiB RSS and used no swap. PostgreSQL was restricted to one CPU. Cgroup lifetime `memory.peak` was 1,073,745,920 bytes against a 1,073,741,824-byte limit; OOM and OOM-kill counters were zero. The peak includes restore and validation as well as derive. A near-peak `memory.stat` sample was mostly file cache (965,124,096 bytes, 873,177,088 inactive); Docker working-set samples peaked at 522.9 MiB during derive and fell to 128.3 MiB afterward. These are different accounting views, and Docker stats were sampled intermittently.

The database reported `IO / BufFileRead` during the derive. Cumulative `pg_stat_database` counters afterward showed 103 temp files and 21,369,823,391 temp bytes. The counters include small validation queries before derive, so they are an upper bound for derive-only spill. The observed run therefore shows that this configuration completed without OOM under the hard limit, with substantial temporary I/O. It does not establish that a larger `work_mem` is safe under concurrent workers or connections.

The host was a 12th Gen Intel Core i7-12700K with 16 logical CPUs and 22 GiB RAM. This was an isolated local clone, not a concurrent three-service test on the user's 5–8 GiB VPS. The snapshot finalization manifest recorded 720 earlier category members; this fresh runtime derive produced 718. Member-level differences were not reconciled, and rolling-window as-of is computed at runtime.

Detailed inputs, exact counters, restore verification, output paths, and limitations are recorded in `.scout-data/diagnostics/compact-memory-benchmark-2026-10-11.json`.
