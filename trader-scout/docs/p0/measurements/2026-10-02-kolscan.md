# 2026-10-02 — kolscan.io probe (candidate-address source, NOT a ranking source)

## What was checked

`kolscan.io` was proposed as a candidate free leaderboard. Fetched two pages via direct `curl`
(no JS execution, no API key) and inspected the raw Next.js App Router server-rendered HTML/RSC
payload directly:

- `https://kolscan.io/` (home page, live trade feed)
- `https://kolscan.io/leaderboard` (the page a "Leaderboard" nav link points to)

## Negative finding: there is no ranked leaderboard

`/leaderboard` returns HTTP 200 at the transport level, but the RSC payload embedded in that
response explicitly renders a **404 "Not Found"** component (`{"children":"404"}` /
`{"children":"Not Found"}` literally present in the `self.__next_f.push(...)` stream) — the route
does not exist server-side; the URL just resolves to the same shell as every other page and shows
the app's own not-found UI.

Both pages' RSC payload embed the **same underlying data structure**: a flat array of
`{wallet_address, name, pfp, telegram, twitter, transactions: []}` objects. Checked specifically
for any ranking signal and found none:

- Zero occurrences of a numeric `pnl`/`realized_pnl`/`rank`/`score`/`winrate`/`win_rate` field
  anywhere in either payload (`grep -oE '"[a-z_]*(pnl|rank|score|winrate)[a-z_]*":[0-9.\-]+'`
  returns 0 matches on both files). The substring "pnl" appears only inside wallet *display
  names* (e.g. `"zeropnl"`, `"boogiepnl"`) and marketing copy ("Analyze the Most Profitable
  Wallets", "...provides realtime transactions, token PnL, and a leaderboard ranking their
  perfor[mance]...") — none of it is actual per-wallet data.
- Every entry's `transactions` field is an empty array `[]` on this particular fetch (both pages)
  — this payload is a **roster** (who kolscan tracks), not activity data.
- Entries appear in **alphabetical order by `name`** in the raw payload (confirmed by inspection:
  names run `ִֶָ`, `✶`, `︎`, ..., alphabetically through to `十九岁绿帽少年` at the end) — this is
  consistent with a curated contact list, not a computed ranking.
- `<meta name="robots" content="noindex">` is present on the page — kolscan does not want this
  page indexed, consistent with it being an internal/unfinished route rather than a public
  leaderboard product.

**Conclusion: kolscan.io does not currently expose a ranked PnL leaderboard, despite a nav link
and marketing copy claiming one exists.** The "How do I get my wallet on the leaderboard?" FAQ
entry found in the home page's RSC payload confirms wallets are added to this roster by manual
curation/DM submission ("DM us your wallet for..."), not by computed ranking.

## What kolscan DOES provide, and is genuinely useful for

A **free, keyless, curated candidate-address list** — real Solana wallet pubkeys someone has
independently flagged as notable traders, each with linked Telegram/Twitter/profile-image
metadata (useful for later manual verification, not for our pipeline directly).

- **Live trade feed** (`/`): real-time `<name> bought/sold <amount> sol (<token amount>) of Spl
  token at $<price> <N>s ago`. Spot-checked 7 distinct `/account/<pubkey>` links on the home page,
  all validated as genuine 32-byte base58 Solana addresses (decoded and length-checked, not
  assumed from format alone).
- **Full roster** (the same data structure served under the dead `/leaderboard` route): on the
  order of 300+ named wallet addresses, pfp/socials attached, candidates for a discovery-candidate
  pool.

This is a legitimate **Tier 2 candidate-address source** for an overlap experiment (P0.7): pull
candidate wallets from kolscan, independently verify their activity via our own
`buyer-intersect`/`wallet-rank`, and compare — exactly the same role GMGN (see
`2026-10-02-gmgn.md`) plays, but free and keyless, at the cost of having no ranking/PnL signal of
its own to compare against (kolscan tells you *who*, not *how good*).

## Method note for future reference

Scraped with two single dated `curl` snapshots, no polling, no authentication, no JS execution
(the Next.js RSC payload is plain text embedded in the initial HTML response — no headless
browser needed to extract the `wallet_address`/`name` list). Any future recurring use of this
source should remain a periodic dated snapshot, not continuous polling, consistent with this
session's prior decision to defer live-watchlist monitoring (P4.5, deferred).
